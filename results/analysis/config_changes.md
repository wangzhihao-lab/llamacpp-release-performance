The same file in the failed tags and in the tags around them (tarballs read only):

| tag | Build result | build-info.cmake sha256 (first 12 digits) | Return-code check |
|---|---|---|---|
| b1137 | ok | cd2a502cd54a | yes |
| b1245 | ok | cd2a502cd54a | yes |
| b1296 | build_failed | 4efa9fc1a94c | no |
| b1381 | build_failed | 4efa9fc1a94c | no |
| b1432 | build_failed | 4efa9fc1a94c | no |
| b1505 | ok | 36c6d69fe42f | yes |

**Cause**: this is not a clang incompatibility. `scripts/build-info.cmake` is identical in the three tags (sha256 equal in the first 12 digits). After finding git it runs `set(BUILD_NUMBER ${COUNT})` without checking that `git rev-list` succeeded. The source comes from a release tarball (no `.git`) and this machine has `/usr/bin/git` (configure log: `Found Git`, `fatal: not a git repository`), so COUNT is empty, `BUILD_NUMBER` is cleared, the generated `build-info.h` contains `#define BUILD_NUMBER ` (empty), and `fprintf(..., BUILD_NUMBER)` reports `expected expression`. The same macro is used in `examples/llama-bench/llama-bench.cpp` (`test::build_number = BUILD_NUMBER`), so compilation after common.cpp would fail for the same reason.

**Evidence**: the tags in the table above that build all have a return-code check (b1137/b1245 use `GIT_HEAD_RESULT`/`GIT_COUNT_RESULT`, later releases use `RESULT_VARIABLE RES` + `if (RES EQUAL 0)`), while the same file in the three failed tags has none.

Commits in the local `repo/` (git metadata read only) between b1245..b1505 that change build-info:

| Commit | Date | Description | First tag containing it |
|---|---|---|---|
| b12fa0d1c | 2023-11-02 | build : link against build info instead of compiling against it (#3879) | b1468 |
| 99115f3fa | 2023-09-25 | cmake : fix build-info.h on MSVC (#3309) | b1273 |
| e6616cf0d | 2023-09-15 | examples : add compiler version and target to build info (#2998) | b1247 |

So one of the two commits after b1245 removed the check and the last commit restored it. Affected are all releases between those two points that are built from a tarball on a machine with git (the three failed tags are among them).

**Minimal patch (the same for the three tags, restores the check logic of b1245)**, applied to `src/<tag>/scripts/build-info.cmake`:

```diff
@@ if(Git_FOUND)
     execute_process(
         COMMAND ${GIT_EXECUTABLE} rev-parse --short HEAD
         WORKING_DIRECTORY ${CMAKE_CURRENT_SOURCE_DIR}
         OUTPUT_VARIABLE HEAD
         OUTPUT_STRIP_TRAILING_WHITESPACE
+        RESULT_VARIABLE GIT_HEAD_RESULT
     )
     execute_process(
         COMMAND ${GIT_EXECUTABLE} rev-list --count HEAD
         WORKING_DIRECTORY ${CMAKE_CURRENT_SOURCE_DIR}
         OUTPUT_VARIABLE COUNT
         OUTPUT_STRIP_TRAILING_WHITESPACE
+        RESULT_VARIABLE GIT_COUNT_RESULT
     )
-    set(BUILD_COMMIT ${HEAD})
-    set(BUILD_NUMBER ${COUNT})
+    if(GIT_HEAD_RESULT EQUAL 0 AND GIT_COUNT_RESULT EQUAL 0)
+        set(BUILD_COMMIT ${HEAD})
+        set(BUILD_NUMBER ${COUNT})
+    endif()
 endif()
```

Effect: BUILD_NUMBER stays at its default 0 and BUILD_COMMIT at `unknown`, matching what the binaries of the other tags report (build_number_reported = 0 in records.csv). Only the build script changes, not the inference code, so performance stays comparable.

**Equivalent approach without changing the source**: between configure and build, add the number to the generated header (without `.git` no rule to regenerate it is registered, so the build does not overwrite it):

```bash
sed -i '' 's/^#define BUILD_NUMBER $/#define BUILD_NUMBER 0/' src/<tag>/build-info.h
```

**Before a re-run**: the patch is not verified (nothing was built). With the same toolchain b1245 and b1505 compile, and the ggml and llama targets finish before the point of failure, so this is expected to be the only blocker. A new error after patching would need its own fix. A re-run should follow build_bench.sh (REPS=5, PARAM_SETS=main) and record the patch in the build_meta of the tag (`patch` key) for traceability.

## Method and limitations

- The runtime configuration comes from records.csv and the raw JSON (values actually used). The `help_*` columns are the defaults the binary declares in `--help`. The two sources corroborate each other.
- Build-option defaults come from interpreting a subset of the CMake files in the tarball (APPLE, arm64, AppleClang, with check results taken from the configure log). Uncertain values carry `?`. From b4318 on the CPU flags are set inside a CMake function, so the flags printed in the configure log are used directly.
- The `eff_*` columns normalize equivalent settings (for example, without a type_k field f16_kv=true is recorded as f16/f16, without n_ubatch it equals n_batch, and mmap=1,dio=0 and load_mode=mmap are both recorded as mmap), so only real changes of the effective configuration are listed.
- A configuration change can be located only between two adjacent sampled tags (sparse sampling).
