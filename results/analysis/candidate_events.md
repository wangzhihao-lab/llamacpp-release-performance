# Step 1: candidate events

Generated by `scripts/analysis/step1_candidate_events.py`. Rule (protocol step 1): 12 series (3 models × 2 back ends × pp512/tg128) are ordered by build number, and the change between adjacent measured tags is compared on the log scale (Δ = ln(new/old), so rises and falls are symmetric): a pair with |ln(new/old)| ≥ τ = max(ln(1+10%), 3 × pooled SD) is a candidate, where the pooled SD pools the SDs of ln(throughput) over the 5 repetitions at each end. In the tables Δ is shown as the percentage exp(ln ratio)−1 and τ as exp(τ)−1 (10% means a rise of +10% or a fall of −9.1%). Candidates with overlapping intervals are merged into event intervals.

- Adjacent tag pairs: 892 (12 series); candidates (series level): 140; event intervals: 54.
- Class counts: A runtime config/default change 2, B build-option change 0, C unexplained 29, D noise suspected 23.
- Noise flags: near = |ln ratio| < 1.25τ; load = load1_before at either end exceeds the Tukey upper fence Q3 + 1.5·IQR of the same model × back end and the change does not persist to the next sample (a persistent change is marked load-but-persistent and is not noise); spike = one-tag spike of a single model (the next sample returns to within ±τ of the old level, all series with a spike in the same direction at that tag belong to one model, and no A/B configuration item changes at that tag and back). A one-tag spike shared by several models is marked shared-spike and is not noise.
- Classes: all series of the interval carry noise flags → D. Otherwise each non-noise series is checked against the likely/possible step-0 changes in the interval whose back end and test scope cover it: all explained → A (an A change is involved) or B; any series unexplained → C, and `class_candidates` lists the classes that explain some of the series. drift (the mean of the last 2 repetitions of a run differs from that of the first 2 by > 15%) and persist (the next sample still deviates from the old level by ≥ τ) are notes only.

## Limitations

- Sparse sampling: only changes visible between sampled releases can be seen. A regression fixed inside an interval, or several changes that cancel out, are not seen, and the duration of an event is known only as an interval (from the previous sampled tag to the next one).
- Each point is one llama-bench call (5 repetitions), so the pooled variation reflects within-run noise only, not noise across measurement periods. Within-run variation of tinyllama/metal and qwen/metal/pp512 often exceeds 10% (the GPU frequency drops during a run), so candidates in these series depend on the re-measurement of step 2.
- Classes A and B only say that a possible configuration or build explanation exists in the interval, not that it is proven. A class B change still looks like an implementation change under the fixed configuration of step 2; separating B from C would need rebuilds with uniform compile options.
- The measurement order is fixed (tinyllama/metal first at every tag) and the first measurement follows the build directly, so load1_before is generally high. The load flag catches only outliers at the same position.
